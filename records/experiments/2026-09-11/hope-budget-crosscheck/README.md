# HOPE 재개 후 예산 집계 교차 확인 — 진행 중

2026-09-11 03:40 KST, Codex 읽기 검사. 수집 wrapper/프로세스는 변경하지 않았다.

`run_hope_pilot.py::Pilot.used()`는 각 과거 stage의 `collect_out` 경로에서 **현재**
`attempts.json`을 다시 읽는다. AlphabetSoup의 03:17:06 실행은 0.1초 동안 입력 검사만
실행했고 실제 episode는 0개였다. 이 기록의 collect_out은 여전히
`out/hope-pilot/AlphabetSoup/executed`다. 재개 작업은 옛 폴더를 quarantine으로 옮기고
같은 경로에 새 실제 실행을 쓰고 있다.

직접 확인: 옛 기록을 따라가면 현재 실제 시도 10개가 나오지만, 보존된 옛 기록
`out/hope-pilot/quarantine/20260911T032726/out/hope-pilot/AlphabetSoup/executed/attempts.json`
에는 metadata 거절 12개, 실제 episode_id 0개다. 새 execute 기록이 추가되면 두 stage가
같은 실제 실행 폴더를 가리켜 12회를 24회로 계산할 수 있다. 이는 성공 판정의 오류는
아니지만, 총48회 예산을 일찍 소진한 것으로 오인해 조건부 배치 확대를 막을 수 있다.

수정 원칙: stage 완료 당시 실제 실행 수와 attempts 파일 해시를 고정하고, 옛 결과의
경로는 quarantine 위치로 보존한다. 같은 경로를 여러 번 읽어 세는 방식은 사용하지 않는다.
과거 입력 오류 stage의 실제 실행 수는0이다. 수집 기준/후보/제어/예산 수치 변경은 불필요하다.
현재 중앙 실제 실행을 중단하거나 이미 생성된 후보를 다시 생성할 이유는 없다.

이 기록은 Claude 담당 코드에 대한 인계다. 수집 종료 시 중복을 제거한 실제 시도 수로
보고하고, 후속 확대의 실행 전 예산을 확인해야 한다. 아직 수정 완료로 기록하지 않는다.

## 04:18 갱신

Claude가 wrapper v4에서 동일 collect_out 경로를 한 번만 세도록 수정하고 재개했다.
현재 실제 중앙 실행24회(AlphabetSoup12+Peaches12) 및 재현2회와 summary가 일치한다.
이번 재사용 이전 폴더는 물리 실행0회였으므로 현재 중복 문제는 해소됐다.
다만 이 방식은 **살아 있는 수집 폴더의 횟수**이며, 과거 quarantine에 물리 실행이 있는
일반적인 재시도까지 자동 합산하는 방식은 아니다. 그런 경우에는 stage 당시 횟수/파일해시와
보존 경로를 별도 귀속해야 한다. 이번 파일럿에 그런 과거 동적 실행이 있었다고 주장하지 않는다.
