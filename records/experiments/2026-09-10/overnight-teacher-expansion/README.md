## 3. 그릇·망치는 왜 0인가 — 원인 특정

그릇 두 유형과 망치 `3_Medium_Wrap`은 **정렬 후 도달 재확인에서 전부 탈락**했습니다.
망치 `2_Small_Diameter`는 9/8/12개가 남았지만 정련에서 모두 탈락했습니다. 처음에는 이를 IK
실패로 적었는데 **틀렸습니다**: 기록의 필드 이름은 `ik_passed`인데 없는 키
(`reached`)를 읽어 모든 기각이 IK 항목으로 들어갔습니다. 집계 코드를 고친 뒤의
실제 사유는 다릅니다.

| 물체 / 유형 | IK 실패 | 충돌(최다 3개) |
| --- | ---: | --- |
| 그릇 `10_Power_Disk` | 27 | `world｜finger_r_link4` 38, `link20` 35, `link16` 20 |
| 그릇 `26_Sphere_4_Finger` | 24 | `world｜finger_r_link4` 52, `link16` 26, `link12` 8 |
| 망치 `3_Medium_Wrap` | 2 | `world｜finger_r_link20` 32, `link4` 28, `link8` 21 |
| 망치 `2_Small_Diameter` | 22 | `world｜finger_r_link20` 45, `link4` 42, `arm_r_link6` 26 |

`world`는 테이블 상판과 다리를 담은 body입니다(확인함). 즉 **자세는 팔이 닿는
곳에 있지만 손가락 끝이 테이블을 뚫습니다.** 그릇은 높이 21.7 mm, 망치는 두께
33.2 mm로 눕혀 놓이므로, 감싸려면 물체 아래로 내려가야 합니다.

그리고 이것은 이미 초기화 단계가 알고 있었습니다. `op=init`의 collision 필터
(평면 검사 `check_plane`이 들어 있는 단계)의 통과 수는

| 물체 / 유형 | collision 통과 / 입력 | 되돌려진 수 |
| --- | ---: | ---: |
| 머그 `3_Medium_Wrap` | **11 / 33** | 22 |
| 그릇 `10_Power_Disk` | **0 / 49** | 49 |
| 그릇 `26_Sphere_4_Finger` | **0 / 41** | 41 |
| 망치 `3_Medium_Wrap` | **0 / 32** | 32 |
| 망치 `2_Small_Diameter` | **0 / 59** | 59 |

입니다. Dexonomy의 `valid_index_padding`이 최소 개수를 채우려고 기각된 후보를
**전부 되돌려 놓기** 때문에, op=init은 테이블을 뚫는 자세를 그대로 내보내고
정렬의 메시 단위 충돌 검사가 뒤늦게 걸러냅니다. 그래서 남는 것이 없습니다.

**시험한 초기화에서는 collision 필터의 통과가 0이었습니다.**
이는 제한된 확대를 중단하고 원인을 조사할 근거이며, 다른 seed·유형의
불가능성을 증명하지는 않습니다. 아래 opt_step 변경에서도 일부 자세는 회복됩니다.

이 0이 테이블 때문에 생긴 것인지도 따로 확인했습니다. 테이블 없는 floating
장면으로 같은 정렬을 돌리면 그릇 0/49·0/41, 망치 0/32로 **완전히 같습니다**.
망치 `2_Small_Diameter`의 정련 0건도 floating에서 0건입니다. 즉 이번 0은
테이블을 정련에 넣은 새 조건의 부작용이 아닙니다.

### 분기 규칙 적용

어디에서도 성공이 없었으므로 `plan.json`의 규칙대로 **가장 멀리 간 물체 하나**
(머그: 유일하게 실행 가능한 후보를 만들었고, 실패가 정렬이 아니라 접촉·리프트에
있는 유일한 물체)를 골라 예산을 24개까지 올리고 **유형 하나만** 추가했습니다.
`1_Large_Diameter`를 고른 이유(머그 몸통이 큰 지름의 원통이고, 관측된 실패가
접촉 미완성과 하중 중 상실이므로 손을 더 많이 대는 쪽을 시도)는 실행 전에
`out/teacher-expansion/expansion.json`에 적었습니다. 결과적으로 고유 후보는
9 → 17개가 됐고, 추가 유형은 5/8이 전 접촉군을 잡는 데까지 갔습니다(기존 두
유형은 4/9). 완주는 여전히 0입니다.

## 4. 캔의 배치 변화

기존 성공을 기준으로, **같은 manifest·같은 seed·같은 후보 3개**를 세계 수직축
yaw만 바꿔 실행했습니다. `placements.json`.

먼저 yaw 전달을 검증했습니다(`scripts/check_yaw_transfer.py`, 새로 작성).
세 가지를 각각 확인합니다: reset이 요청한 회전을 위치를 유지한 채 그대로
적용하는가, teacher 자세가 물체 기준인가(장면 설정에서 물체가 원점에 있음을
읽어서 확인), 그래서 목표가 물체를 따라 도는가. 캔은 ±7.5°·±15°·±22.5° 전부
**reset 오차 0, 목표 오차 ≤ 5.6e-17 m / 3.7e-08 rad**로 통과했습니다.

| 배치 | 시도 | 완주 | 나머지 결과 |
| --- | ---: | ---: | --- |
| −22.5° | 3 | 0 | 접촉 미획득 2, **접근 경로 실패 1** |
| −15° | 3 | 0 | 접촉 미획득 2, **끝까지 유지 중 tick 예산 소진 1** |
| −7.5° | 3 | 0 | 접촉 미획득 2, 끝까지 유지 중 tick 예산 소진 1 |
| **0°** | 3 | **1** | 접촉 미획득 2 |
| +7.5° | 3 | 0 | 접촉 미획득 2, 획득 후 상실 1 |
| **+15°** | 3 | **1** | 접촉 미획득 2 |
| +22.5° | 3 | 0 | 접촉 미획득 2, 끝까지 유지 중 tick 예산 소진 1 |

세 후보 중 완주하는 것은 언제나 같은 후보(`0_96_grasp.npy`,
`9d7009a7406f7304…`, `10_Power_Disk`)이고, 나머지 둘은 어느 배치에서도 전
접촉군을 잡지 못합니다.

**"tick 예산 소진"을 과제 실패의 한 유형으로 구분했습니다.** −15°의 경우 5/5 접촉군을 792
tick 유지하고 148.0 mm까지 올린 채 hold 단계에서 1,450 tick 한도에 걸렸습니다
(종료 직전 연속 유지 14 tick, 완주한 실행들은 50 tick). 성공 기준도 tick 예산도
바꾸지 않았고, 이 실행들을 시범으로 세지도 않았습니다. 다만 "잡지 못했다"고
적는 것은 사실과 다릅니다.

## 4-2. 추가 조건 — 매처 반복 수를 줄이면 테이블 여유가 남는가

시험했습니다. **`op.matcher.opt_step`만** 25 → 10 → 4로 바꾸고 나머지는 모두
같습니다(같은 물체·유형·seed·필터 입력·테이블 포함 장면·rest 0·yaw 0·같은
후보 선택 규칙). 고정 조건과 섞지 않도록 별도 조건으로 적고, 결정과 근거는
실행 전에 `out/teacher-expansion/opt-steps.json`에 남겼습니다.

**가설은 맞았습니다.** 정렬 후 도달 재확인을 통과한 수(seed 0·1·2):

실패 구성은 다릅니다. 두 조건 합계 32건 중 전 접촉군이 동시에 관측된 것은
**12건**(8+4)입니다. 전 접촉 존재만으로 안정적인 파지나 닫기 완료를 뜻하지 않습니다.

### 정련기는 왜 거부하는가

`hydra.verbose=true`로 후보별 거부 사유를 켜서 다시 돌렸습니다.

| 실행 | 거부 사유 |
| --- | --- |
| 망치 `2_Small_Diameter` | 42/42 **요구 접촉 body 미달성** — 유형이 `finger_r_link7`·`link8`을 요구하는데 실제 접촉은 약지·소지 쪽 |
| 망치 `3_Medium_Wrap` | 9/9 같은 사유(요구 쌍 3종 모두) |
| 그릇 `10_Power_Disk` | 2/2 같은 사유 |

위 디버그 재실행에서 기록된 거부 사유는 **요구 접촉 body 미달성**입니다.
접촉 매핑·초기화·최적화 수렴·형상/유형 적합성을 추가로 분리해야 합니다.
이 거부 로그만으로 물리적 불가능성을 증명하거나 다른 품질 검사가 통과한다고
주장할 수는 없습니다. 아직 도달하지 않은 검사의 실패 가능성도 남습니다.

이번 예산과 분기 규칙에 따라 확대를 멈췄습니다. 후속 조건과 평가 분모를 미리
고정한 유형 비교는 가능하며, 개발 단계의 탐색 자체가 증거를 무효로 하지는 않습니다.

두 가지를 그대로 적어 둡니다.

1. `MUJOCO_GL`이 **설정되지 않은** 환경에서 전체 스위트를 돌리면
   `tests/test_mask_visibility_audit.py`의 렌더링 테스트가 실패합니다.
   `tests/test_fixed_student.py`가 import 시점에 `MUJOCO_GL=egl`을 설정해
   건너뛰기 조건이 풀리기 때문이며, **제 변경 이전부터 있던 문제**입니다
   (새 테스트 파일을 모두 제외해도 재현됩니다). 두 파일 모두 시각·student
   영역이라 손대지 않았습니다. 제 쪽 원인은 없앴습니다 —
   `tests/test_yaw_transfer.py`는 import 뒤 환경 변수를 원상복구합니다.
2. 정렬 기각 사유를 처음에 "전부 IK 실패"로 적었던 것은 잘못이며, 위 3절이
   수정된 내용입니다. 원인은 존재하지 않는 키를 읽은 집계 코드였습니다.

## 7. 다음에 할 일

- **그릇·망치처럼 낮게 눕는 물체**: 4-2절에서 병목이 한 단계 더 좁혀졌습니다.
  정렬의 테이블 여유는 매처 반복 수를 줄이면 되찾을 수 있지만, 그래도 정련이
  0건이고, 확인한 디버그 재실행은 **요구 접촉 body 미달성**으로 거부합니다.
  접촉 매핑·최적화 실패와 형상/유형 부적합을 구분하는 것이 다음 진단입니다. 선택지는 (a) 다른 놓임 자세를 쓰거나, (b) 그 형상에서 요구 접촉이
  실제로 성립하는 유형을 쓰는 것입니다. (a)는 rest 전달이 구현·검증되기
  전까지 실행하지 않습니다(이번에 yaw는 검증했고 rest는 아직입니다). (b)는
  **teacher 단계의 접촉 도달 검사**를 후보 우선순위에 활용할 수 있습니다.
  실패를 물리적 불가능 판정으로 쓰지 말고, 검증된 병·캔 양성 대조군과
  body 매핑·접촉 위치·거리·법선 잔차를 함께 확인해야 합니다.
- **머그**: 실패가 하중 중 접촉 상실에 몰려 있습니다. 닫기 제어는 이번에
  건드리지 않았으므로 별도 실험으로 남깁니다.
- **캔**: 시범 2건이 같은 teacher 후보에서 나왔습니다. 후보 다양성을 늘리는
  것이 시각 student 학습에는 더 필요합니다.
