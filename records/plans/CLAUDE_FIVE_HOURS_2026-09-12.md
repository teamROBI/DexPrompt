## 0. 실행기와 사전 검사 — 최대40분

새 `scripts/run_teacher_followup_5h.py`를 구현하고 먼저 테스트한다. 이 파일은 아직 존재하는 명령이라고 가정하지 않는다.
기존 검증된 수집/배치/보고 함수를 재사용하되 이전 실행기의 날짜·총예산 상수를 바꾸지 않는다.
CLI 계약:
`--out <새 폴더> --hours 5 --workers 2 --max-physics-runs 163 [--resume]`

- T0, deadline, cutoff, 후보·순위·배치·seed·코드 해시를 실행 전에 plan.json으로 고정.
- 새 물리 실행은 T0+4시간15분 이후 시작하지 않는다. 물리 실행을 T0+4시간40분까지 정리하고 마지막20분은 보고.
- 각 물리 시도는 최대240초. timeout은 자체 process group만 종료하고 인프라 오류로 기록.
- 시작 전에 UUID/후보/조건을 원장에 기록하고 예산을 예약한다. 동시2개에서도 예산 초과나 중복 실행 금지.
- started/completed/accepted/infra_error/timeout/reproduced를 구분. 시작한 시도는 실패와 무관하게 비용 차감.
- stage별 시작/종료/PID/exit/timeout/로그, 상태의 원자적 저장. 상위 단계 실패시 종속 단계 중단.
- resume은 같은 plan과 산출물만 사용. 살아 있는 PID가 있으면 중복 시작 거부. 중단된 부분 출력을 성공으로 재사용하지 않는다.
- SIGTERM 및 deadline에서 본인 child process group을 정리하고 가능한 마지막 보고를 작성. 사용자 이름/프로세스 이름으로 일괄 kill 금지.
- 모든 출력은 `/data1`의 새 폴더. root/tmp에 대용량 모델을 누적하지 않는다.
- 공간을 사전 검사하고, 본인 생성 모델의 동일 해시 파일만 중복 저장을 줄인다. 기존 사용자 파일 삭제 금지.
- BLAS/OMP/MKL1thread, nice15, 동시 물리2개. GPU가 필요하면 가용 상태 확인 후 사용하며 다른 작업을 중단하지 않는다.

40분 안에 신뢰할 수 있는 실행기를 만들지 못하면 준비 완료 범위와 장애를 기록하고 종료한다.

## 1. 선정 점수 정정 — 새 물리 최대13회

확인된 사실:
- Raisins raw logits는 -241.7~-193.7,16개 모두 다르지만 float32 sigmoid가 모두0으로 만들어 해시 순으로 정렬됐다.
- AlphabetSoup·Peaches의 보관 확률도 각각16개 모두 다르다. 기존14/10개 고유값 및 Peaches 동점 서술을 정정한다.
- 낮은 train loss만으로 과적합을 확정하지 않는다. 가설로 표현한다.

실행:
1. checkpoint·입력·기존 순위 해시를 확인한다. raw logit 내림차순, 실제 동점만 해시 순으로 정렬한다.
2. 유한성 및 -250/-200처럼 sigmoid가 함께0이 되는 경우에도 순위가 유지되는 회귀 검사를 추가한다.
3. 기존 rankings.json은 유지하고 rankings-logit.json을 별도로 고정한다. 평가 결과를 보고 모델/설정을 바꾸지 않는다.
4. 물체별 기존 성공 대조군을 재현(최대3회). 실패한 물체의 새 물리 실행은 중단하고 다른 물체는 계속한다.
5. 원래 평가16개 중 아직 실행하지 않은 후보만 실행한다. 기존합집합41개이므로 새 실행은 최대7회다.
   원래41개 결과의 모델/배치/제어 계약을 확인해 재사용한다. 이미 완료된 후보를 또 평가하지 않는다.
6. 각 물체에서 logit top8의 첫 성공 중 동일 조건 재현이 아직 없는 것만 재현한다(최대3회).
7. 원래 선정 절차 결과와 logit 정정 결과를 나란히 보고한다. 이미 본 평가 풀의 사후 구현 정정 검증이지
   새로운 독립 test나 새로운 일반화 증거가 아니다. 원래 결과를 수정된 결과로 대체하지 않는다.

완전한 평가풀이 되면 accepted/16, 각 top8의 accepted/8, 선택 교집합·추가 선택 후보,
기존 결과 재사용/새 실행 수, 누락·인프라 오류를 함께 쓴다. 누락을 실패로 채우지 않는다.

## 2. 배치 시범 수집 — 최대150회

추가 선정기 튜닝 대신, 이제 확인된 성공 후보에서 다양한 배치의 teacher 시범을 확보한다.
이 단계는 데이터 수집용 개발 실험이다. 단계1의 평가 풀을 이후 학습 자료로 쓰면 그 사실을 표시한다.
이 풀을 향후 최종 평가용으로 다시 사용하지 않는다.

### 후보 고정

- A 물리의 중앙 단일 조건에서 accepted된 후보를 기존 및 이번 기록에서 합치고 후보 해시로 묶는다.
- 물체당 최대2개, 총최대6개를 고른다. 가능한 한 서로 다른 후보를 사용한다.
- 원 episode의 QualityLimits를 사용해
  `min((침투한계-최대침투)/침투한계, (힘한계-최대힘)/힘한계)`가 큰 후보 순으로 고른다.
  동률은 후보해시 순. 이는 투명한 수집용 규칙이며 학습 선정기의 성능으로 세지 않는다.
- 새 배치 실행 전에 후보 목록·선택근거·원본 episode/모델/초기상태/scene/mesh/teacher 해시를 고정한다.
- 선택한 후보의 중앙 상태 재현은 최대6회. 기존 이번실험 재현이 완전히 같은 계약이면 재사용하고 중복 비용을 쓰지 않는다.
- 중앙 재현 실패 후보는 배치 단계에서 제외하며 다른 후보로 사후 대체하지 않는다.

### 고정 배치12개 / 후보

공통 중앙 배치에 대해 아래 한 요인 변화만 적용한다. X/Y는 기존 장면의 world 축, yaw는 기존 yaw 전이 계약을 따른다.
- X: -20, -10, +10, +20 mm (4개)
- Y: -20, -10, +10, +20 mm (4개)
- yaw: -15, -7.5, +7.5, +15도 (4개)

높이·rest pose·scale·질량·물리·제어·필수 접촉군은 바꾸지 않는다. teacher reference도 물체와 함께 정확히 전이한다.
배치/메시/scale/관절/테이블·초기 안정화 계약, 초기 겹침/가시성을 검사한다.
사전 검사 실패 조건은 제외 사유를 기록하고 다른 배치로 대체하지 않는다.
사전 검사에서도 실제 시뮬레이션을 돌리면 횟수와 물리 시간은 별도 원장에 공개한다.

- 새 전체 파지 실행: 최대6후보×12배치 =72회.
- 새 배치에서 accepted된 각 시범은 동일 조건으로1회 재현: 최대72회.
- 중앙 재현 최대6 + 새 배치72 + 재현72 = 최대150회.
- 전체 파지 실행 상한: 단계1 최대13 + 단계2 최대150 = **163회**. 재시도도 이 상한에 포함한다.
- 시간/공간/예산이 부족하면 계획 순서대로 중단한다. 물체→후보를 round-robin으로 실행해 한 물체에 예산을 몰지 않는다.
- 실패 조건을 그 자리에서 튜닝하지 않는다. accepted가 없어도 대조가 정상인 다른 사전 고정 조건은 진행한다.
- 재현하지 못한 accepted는 `reproduction_pending/failed`로 남기고 검증 완료 시범 수와 구분한다.

## 실행 명령 — 실행기 구현·검사 후에만 실행

아래 launcher는 실행기 파일이 없으면 즉시 실패해야 한다.
실제 실행기 인터페이스를 위 계약대로 만든 뒤 사용하고, 실행 전 전체 plan을 디스크에 저장한다.
`--resume`은 tmux가 살아 있을 때 사용하지 않는다.

실행 시작 시 새 출력 폴더의 plan.json에 기록된 T0를 기준으로 모든 deadline을 계산한다.
준비 단계에서 이미T0를 고정했다면 실행기 시작 때 초기화하지 말고 남은 시간만 사용한다.
바깥 timeout은 최후의 제한이며 실행기 자체의 자식 정리·FINAL 작성 기능을 대신하지 않는다.

```bash
cd /home/yspark/projects/ICRA
bash scripts/launch_teacher_followup_5h.sh /data1/yspark/sim/icra/teacher-followup-5h-20260912-v1
```

위 launcher는 이번 지시 준비 중 작성됐고 bash syntax 검사만 수행했다.
실험 실행기 `run_teacher_followup_5h.py`는 아직 구현하지 않았으며, 물리 실행은 시작하지 않았다.
Claude가 Python 실행기 구현·검사와 조건 고정을 완료한 후 launcher를 실행해야 한다.
백그라운드 LLM 대기가 아니라 실행기 자체가 단계 전환·조건부 진행·최종 보고까지 수행해야 한다.
