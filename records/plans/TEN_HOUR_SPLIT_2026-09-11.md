전체 논문 근거·분석·원고 완성도는 **약 30–40%, 대표값 35%**라는 계획용 주관적
추정을 유지한다. 코드 완성률이나 채택 확률이 아니다. 설치/테스트 개수로 올리지 않는다.
P3/P5가 통과해야 그 다음 일반화 실험의 규모와 예상 기간을 현실적으로 정할 수 있다.

HOPE는 28개 공식 메시의 단위 감사, 파일럿 6개 자산 생성, 30개 초기 장면 검사를
마쳤다. AlphabetSoup/Peaches/Raisins만 각각 5개 배치 통과. **15개 시범이 아니라
15개 초기 장면**이다. 보고서로 확인된 HOPE 동적 성공은 아직 없다.

계획 작성 시 lecun x0: **790/6,331 updates**, loss 0.01440(그 시점 집계), 학습 잔여
약 6,296초. `dexprompt-x0-bc` tmux 진행 중. 성공률은 아직 없다.
기존 epsilon loss와 x0 loss는 목적 함수가 달라 숫자로 성능을 비교하지 않는다.

3. 승인 가능한 새 student 데이터 목록(0건도 명시), 다음 한 실험의 선택 근거.

## Claude의 실행 범위

입력은 `out/hope-pilot-v1/generation-plan.json`과
[HOPE 파일럿 보고서](../experiments/2026-09-11/hope-pilot/README.md)다.

1. **중앙 조건 우선:** AlphabetSoup, Peaches, Raisins. 각 물체 정식 템플릿 2개는
   계획대로 고정한다. AlphabetSoup/Peaches: Power Disk·Large Diameter,
   Raisins: Palmar Pinch·Large Diameter. 템플릿 내용 해시, 접촉점 선택, seed와
   후보 귀속을 기록한다. align seed 0/1/2, refine 400회. 예측 수·matcher·필터 예산도
   첫 실행 전에 저장하고 이후 결과를 보며 바꾸지 않는다.
2. **중앙 동적 실행 최대 12회/물체, 총 36회.** 접근 실패도 분모에 포함한다.
   후보 선택/순서는 이미 실행 중인 `build_expansion_manifest`의 내용 hash 정렬→중복 제거→상위12 규칙을 유지한다.
   이는 유형/seed 균형 배분이 아니므로 실제 선택 수를 유형/seed별 보고한다. 동일 후보 재실행을 독립 성공으로 세지 않는다. 후보가 부족하면 있는
   것만 실행하고 부족 사유를 기록한다.
3. 중앙 첫 성공 후보는 물체당 1개까지 동일 조건으로 1회 재현한다(최대 3회).
   재현 실패는 확대 조건을 만족하지 않는다. 전체 contact/quality 판정과 episode
   hash를 대조한다. 해시가 다르면 물리 신호의 차이를 조사하고 동일 재현으로 쓰지 않는다.
4. **중앙에서 재현한 물체만 확대:** 동일한 첫 성공 후보 1개를 사용해 yaw ±15°,
   X ±20 mm 네 조건을 각각 1회 실행한다. 최대 12회. 이미 검증한 yaw/배치 변환을
   적용하고 조건마다 전체 접근부터 실행한다. 배치마다 teacher/물체/테이블 상대좌표를
   확인한다. 새 배치의 성공은 조건당 1회 재현(최대 12회). 실패 조건의 추가 튜닝 없음.
   scene YAML에 yaw가 들어 있으므로 episode yaw는 0; 회전 중복 적용 금지.
5. 총 상한은 **새 동적 시도 48회 + 재현 15회 = 63회**다. 첫 중앙 36회가 우선이며
   확대는 조건부다. 재현 시도는 별도 열로 보고한다. 이 수는 성공 시범 목표가 아니다.
6. 기존 contact-feedback closure, 품질/성공 기준, 질량·마찰·접촉 파라미터를 유지한다.
   그릇/망치/불안정 HOPE 3개는 이 작업에 다시 넣지 않는다. table hook이 실제 적용되고
   init padding 출력이 통과로 집계되지 않는지 확인한다.
7. wrapper에서 단계 exit code/timeout/실행 명령/원본 로그를 남긴다. `no_candidates`,
   정상 물리 실패, 예외, timeout, 예산 미실행을 구분한다. subprocess timeout 때
   자식이 띄운 하위 실행도 남지 않는지 검사하고, 종료는 자신이 시작한 프로세스에만 한정한다.
8. 결과를 물체가 끝날 때마다 인계: candidate manifest, episode npz, 모델/초기상태
   archive, scene/asset/template hashes, 단계 판정, 접촉군, 위치/힘/침투 신호, 실행 명령.
   accepted 목록과 rejected 진단 경로를 분리한다. Codex가 전체 종료를 기다릴 필요 없다.

CPU는 시작 시 workers 2·BLAS 1·nice 15. GPU 단계는 실제 환경이 준비된 서버에서
명시적으로 장치와 tmux를 선택한다. lecun GPU 0에는 Codex의 학습이 있으므로
추가 대형 모델을 겹쳐 띄우지 않는다. 다른 GPU는 메모리/프로세스를 확인하고 작은
teacher 작업 1개만 사용한다. 현재 다른 장치가 비었다고 가정하지 않는다.
새 학습은 lecun 전용이다. 기존 서버에서 teacher 생성이 이미 돌고 있으면 그 작업을
중단하거나 환경 이전을 처음부터 반복하지 말고 사용 위치를 보고한다.

## Codex의 실행 범위와 분기

1. 실행 중인 x0는 그대로 완료한다. 원본 코드/모델과 분리한
   `lecun:out/student-x0-code-v1`, `out/single-bottle-x0-job-v1`을 사용한다.
   13 epochs, seed42, 6,331 updates, 최종 epoch13이라는 선택을 바꾸지 않는다.
   학습 중 loss만 보고 조기 성공 선언/추가 하이퍼파라미터 탐색을 하지 않는다.
2. 기존 자동 평가 5 checkpoints ×3 seeds를 확인한다. epoch13이 주 결과이고
   중간 epoch는 학습 경과 진단이다. 시간 초과나 예외를 0% 파지 성공률로 덮지 않는다.
3. **최종 3회 중 완주가 있으면:** 같은 epoch13을 사전 지정한 추가 seed3000–3009에서
   10회 평가한다. 기존 epsilon 최종도 같은 10개 seed로 별도 원본 코드에서 비교한다.
   동일 시작 상태에서 diffusion 잡음만 바꾸는 견고성 검사이며 물체 일반화가 아니다.
   모델을 고르기 위한 개발 seed로 재사용하거나 좋은 중간 checkpoint로 교체하지 않는다.
4. **최종 0/3이면:** 새 학습을 바로 추가하지 않는다. frame0/200/450/700 및 같은
   sampling seed에서 action 생성 오차, 첫 50 tick에서 arm/hand 오차와 최초 품질
   위반을 비교한다. x0 예측 목표에 맞게 진단 코드를 검사한다(기존 epsilon 해석을
   그대로 씌우지 않는다). 기록 명령 양성 대조군과 학습 과제/샘플링 경로를 비교하고
   다음 단일 요인 실험만 제안한다. epsilon 예산 연장·PPO·rate 제한을 동시에 바꾸지 않는다.
5. 어느 분기든 Claude가 승인한 시범을 받으면 기존 visual-v2 경로로 재렌더한다.
   pre-action 상태/관측·post-action 접촉 신호, timestamp, 27관절 순서, 전체 mask와
   goal memory의 온라인/오프라인 정합을 확인한다. 동일 물리 명령 재생은 원본과
   대조한다. 영상 생성 후 물리 성공 기준을 다시 확인하고 이미지가 생겼다고 채택하지 않는다.
6. 새 데이터는 `out/hope-student-pilot-v1` 같은 새 경로에 만든다. 실패/중복/테스트
   후보가 기존 단일 병 학습에 섞이지 않게 한다. 고유 object·mesh·placement·teacher
   수를 따로 집계한다. 동일 초기 관측에 다른 teacher 경로가 붙으면 표기하고 하나의
   결정론적 라벨로 잘못 간주하지 않는다.
7. 이번에 탐색/선별한 HOPE 3개는 개발용이다. 같은 물체의 새 yaw를 새 형상 test로
   부르지 않는다. 독립 validation/test가 없으면 diagnostic train-only로 표시하고,
   임의의 frame split을 이용해 독립 validation처럼 만들지 않는다.
8. 새 시범이 없으면 기존 캔 데이터를 기준으로 인수 검사를 검증하고 준비 완료까지만
   보고한다. 이번 10시간에는 HOPE 혼합 대량 학습, 새 architecture 탐색, PPO 재탐색을
   추가하지 않는다. 공유 GPU 경쟁으로 평가 시간이 길면 데이터 검사/보고를 CPU로 진행한다.
