# 다물체 후보 사전 검토 — CPU, 학습 없음

현재 기본 놓임 자세(`rest_index=0`)에서는 고정한 100개 후보 모두 정적 검사에서 탈락했다. 기존 완주 병 후보는 동일 검사를 통과했고, 100개의 원본·스케일·접촉 라벨 검사는 모두 통과했다. 이 결과는 IK 실패율이나 파지 성공률이 아니다. IK 실행 수는 **0**이다.

같은 후보들의 물체 놓임 자세만 바꾼 사후 진단에서는 카메라 4개, 캔 4개, 휴대전화 3개가 정적 검사를 통과했다. **기본 자세의 결과를 대체하지 않으며, 이 11개도 학습 가능한 시범으로 인증한 것은 아니다.**

## 범위와 입력 고정

- 기존 `third_party/dexonomy/output/evo_hx5_d20/succ_grasp` 4,495개 파일 / 60개 물체를 목록화했다. `succ_grasp`는 원본 생성기의 판정이며, 현재 로봇의 테이블 접근·리프트 완주를 뜻하지 않는다.
- 그릇·카메라·캔·휴대전화·머그컵에서, 자산이 있는 물체를 이름순으로 하나씩 골랐다. 성능을 보고 물체를 바꾸지 않았다.
- 유형은 `14_Tripod`, `33_Inferior_Pincer`, `6_Prismatic_4_Finger`, `8_Prismatic_2_Finger`. 유형 안에서 내용 SHA256 순으로 정렬하고 유형을 번갈아 선택해 물체당 20개로 고정했다. 유형별 보유 수가 달라 정확히 5개씩은 아니다.
- 검사 전에 [plan.json](../../../out/cpu-multiobject-screen-20260909/plan.json)에 원본 파일·해시·유형·물체·스케일·메시와 충돌 조각 해시·장면 설정·검사 코드 해시를 저장했다.
- 단일 프로세스, 수치 연산 스레드 1개, `nice 10`, GPU 비활성화. 렌더러 호출은 예외로 차단했다. 훈련·동적 실행·영상 생성은 하지 않았다. 주 검사는 약 6.8초였고 정적 진단을 추가했다. 생성물은 약 1.3 MiB다.
- Claude 작업의 공유 코드·학습 출력·원본 후보는 수정하지 않았다. 이 디렉터리와 `out/cpu-multiobject-screen-20260909`에만 작성했다.

## 주 검사: 기본 놓임 자세

| 물체 | 입력 | squeeze에서 테이블 충돌 | open 검사 탈락* | 통과 | 테이블 침투 깊이 중앙값** |
|---|---:|---:|---:|---:|---:|
| 그릇 | 20 | 20 | 0 | 0 | 71.4 mm |
| 카메라 | 20 | 20 | 0 | 0 | 66.5 mm |
| 캔 | 20 | 18 | 2 | 0 | 36.6 mm |
| 휴대전화 | 20 | 20 | 0 | 0 | 93.7 mm |
| 머그컵 | 20 | 19 | 1 | 0 | 57.0 mm |
| 합계 | 100 | 97 | 3 | 0 | — |

\* 기존 코드의 단계명은 `open_hand_inside_object`이지만 이 함수는 벌린 손의 물체 접촉과 테이블 충돌을 함께 검사한다. 해당 3개는 실제로 **둘 다** 발생했다. 표는 순차 검사에서 최초 탈락한 단계이며, 모든 충돌의 상호 배타적 분류는 아니다.

\** 테이블과 충돌한 후보마다 squeeze 자세의 최대 침투 깊이를 구한 뒤 그 중앙값을 계산했다. 전체 97개에서 가장 얕은 침투도 3.06 mm다. 단순한 수치 오차 수준의 표면 접촉만으로 모두 탈락한 것은 아니다. 정적 접촉 계산값이며 동적 접촉력은 측정하지 않았다.

검증:

1. 고정 성공 병 후보 `grasp_38_r120_d0`의 원본 해시 `05b63bfb…`를 확인했다. 동일 Probe에서 squeeze 테이블 충돌 없음, open 물체·테이블 접촉 없음으로 통과했다. 동적 완주를 이번에 재실행한 것은 아니다.
2. 100개 모두 `checked_candidate`의 원본 해시, HX5 식별, 유형, 물체 식별, grasp/squeeze root 일치, 스케일, 접촉 라벨 검사를 통과했다. 이 검사는 탈락 사유를 확인하기 위해 정적 필터를 우회해 별도로 수행했으며 통과 후보로 재분류하지 않았다.
3. 물체 좌표계의 Probe 테이블을 저장된 놓임 자세로 world에 변환해 높이 0·법선 +z를 확인했다. 이는 좌표 변환 검증이며 실제 안정화 후 물체 자세를 보장하지 않는다.
4. 주 검사 중 추적한 공유 소스 해시 변화가 없었고, 진단 뒤 원본 후보 100개의 해시도 그대로였다.

## 사후 진단: 같은 100개, 다른 저장 놓임 자세

물체 자산의 안정 자세 목록을 전수 적용하고 테이블 평면만 해당 물체 좌표계로 다시 변환했다. 손가락·teacher root·스케일·필터 기준은 바꾸지 않았다. 주 검사 결과를 본 후 수행했으므로 사후 민감도 진단으로 구분한다.

| 물체 | rest index 순서대로 정적 통과 수 | 어느 자세에서든 통과한 고유 후보 |
|---|---|---:|
| 그릇 | 0, 0 | 0 |
| 카메라 | 0, 0, 4, 0, 0, 0 | 4 |
| 캔 | 0, 0, 0, 0, 0, 0, 1, 3 | 4 |
| 휴대전화 | 0, 1, 0, 3, 0 | 3 |
| 머그컵 | 0, 0, 0, 0, 0, 0, 0, 0 | 0 |

휴대전화의 합계가 4가 아니라 3인 것은 한 후보가 두 놓임 자세에서 통과했기 때문이다. 후보 원본 경로와 rest index·자세를 [rest-pose-diagnostic.json](../../../out/cpu-multiobject-screen-20260909/rest-pose-diagnostic.json)에 보존했다. 별도 학습용 manifest에는 넣지 않았다.

이 결과가 뒷받침하는 해석은 **일부 기존 floating 파지가 현재 선택된 물체 놓임 자세와 맞지 않는다**는 것이다. 모든 Dexonomy 후보가 나쁘다거나 해당 물체가 물리적으로 파지 불가능하다는 결론은 아니다. 세계 수직축 yaw만 돌리면 손과 테이블의 상대 높이는 유지되므로, 이 정적 테이블 침투를 yaw 탐색만으로 없앨 수 없다.

## 다음 구현·실험 순서

1. 현재 PPO 비교는 유지한다. 이번 검토는 그 보상이나 게이트를 바꿀 근거가 아니다.
2. 다물체 확장 전에 **object + scale + rest index + yaw + teacher hash**를 하나의 실행 조건으로 기록하고, 선별·전체 장면 생성·reset·수집에서 같은 놓임 자세를 사용하도록 연결한다. 현재 이 감사가 사용한 `Probe`와 `reachable_yaws` 경로는 기본 놓임 자세 0을 사용하므로, 위 11개를 그대로 기존 manifest에 넣어서는 안 된다.
3. 실험 목적상 다른 놓임 자세를 허용한다면, 먼저 위 카메라·캔 후보를 실제 장면에 정확히 배치하고 안정화한 뒤 정적 조건을 재확인한다. 이어 목표 IK → 전체 접근 경로 → 닫기·리프트 → 외력 검증 순으로 진행한다. rest index를 이름만 전달하고 실제 모델에 반영하지 않는 오류를 먼저 막는다.
4. 기본 놓임 자세를 유지해야 한다면 그 자세에서 새 후보를 생성·정렬한다. 특히 그릇·머그컵은 이번 20개에서 대체 놓임 자세만으로도 통과 후보가 없었다. 더 넓은 후보 집합 또는 테이블을 고려한 새 정렬이 필요한지 별도로 비교한다.
5. 완주가 검증된 시범이 확보된 후 다물체 BC를 연결한다. 이번 정적 결과만으로 다물체 학습을 시작하지 않는다.

## 감사 코드 정정 및 산출물

주 검사 이후 감사 스크립트 자체의 두 항목을 수정했다. 공유 프로젝트 코드 변경은 없다.

- `Arm.solve`의 세 번째 인자 0.005는 위치 허용 오차가 아니라 damping이었다. 실제 목표 허용 오차는 위치 0.001 m, 자세 0.01 rad다. 원본 실행의 `plan.json`은 증거 보존을 위해 유지하며 그 안의 `ik_position_tolerance_m: 0.005` 표기는 잘못된 것으로 정정한다. 실제 IK 호출은 0회여서 결과에는 영향이 없다. 현재 `screen.py`는 정확한 항목을 기록한다.
- `serialize` 직후의 접촉군은 tuple이다. JSON manifest를 읽는 `checked_candidate`의 list 비교 경로와 맞추기 위해 검사 전에 JSON 왕복 변환을 추가했다. 주 검사에서는 정적 통과가 없어 해당 분기가 실행되지 않았다. 이후 진단에서는 정정한 변환으로 100개 및 양성 대조군의 메타데이터 검사를 실제 실행했다.

실행 당시 `screen.py`와 추적한 공유 소스는 출력 디렉터리에 복사돼 있다. 현재 소스와 최초 실행 복사본이 위 정정 때문에 다른 것은 의도적이다. 출력 디렉터리가 이미 있으면 주 스크립트는 덮어쓰지 않고 실패한다.
